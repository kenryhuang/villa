# 生产建筑院落系统设计

## 目标

所有会产生可收取物品的建筑升级为统一的“生产院落”：建筑拥有明确的 3×3 或 4×4 占地，四周建立与建筑风格匹配的封闭围栏，建筑主体位于院落后半部分，所有制品放在围栏内侧前方的收货区。整个院落在网格、寻路和物理移动层面均不可穿越，玩家站在围栏外即可悬停、查看数量并点击收取产物。

## 适用建筑与尺寸

| 建筑 | 新占地 | 主体原占地 | 围栏风格 |
|---|---:|---:|---|
| 工作台 | 3×3 | 1×1 | 木作 `timber` |
| 石窑 | 3×3 | 2×2 | 石木 `masonry` |
| 熔炉 | 3×3 | 2×2 | 工业 `industrial` |
| 风车 | 3×3 | 2×2 | 木作 `timber` |
| 食品工坊 | 4×4 | 3×2 | 木作 `timber` |
| 纺织机 | 3×3 | 2×2 | 木作 `timber` |
| 鸡舍 | 3×3 | 2×2 | 木作 `timber` |
| 蜂箱 | 3×3 | 1×1 | 木作 `timber` |
| 伐木场 | 4×4 | 3×2 | 木作 `timber` |
| 采石场 | 4×4 | 3×3 | 石木 `masonry` |
| 矿场 | 4×4 | 3×3 | 工业 `industrial` |

温室、水车、水井、谷仓、路灯和装饰围栏不纳入生产院落系统。

## 数据模型

每个适用建筑在 `GameData.BUILDINGS` 中声明 `production_yard`：

```gdscript
"production_yard": {
    "size": Vector2i(3, 3),
    "structure_footprint": Vector2i(1, 1),
    "style": "timber",
    "building_offset_z": -0.35,
    "output_capacity": 6,
}
```

- `size` 是权威网格占地，也是建造预览、拆除和存档中的占用范围。
- `structure_footprint` 保留主体原始大小，用于主体碰撞、交互范围、维修费用以及锤子和状态图标定位。
- `style` 只能是 `timber`、`masonry` 或 `industrial`。
- `building_offset_z` 将建筑主体向院落后方轻微移动，为前排收货区留出空间。
- `output_capacity` 是院落内可显示产物模型的最大种类数；3×3 为 6，4×4 为 8。

`BuildingData.from_dictionary` 解析并验证这组配置。适用建筑缺少或声明非法院落配置时，数据无效并禁止进入建造目录。

## 组件结构

新增 `BuildingProductionYard`，由 `BuildingInstance` 自动创建和管理：

```text
BuildingInstance
├─ VisualRoot
│  ├─ 建筑主体
│  ├─ 活动动画
│  └─ 维修状态
├─ ProductionYard
│  ├─ BackFenceLayer
│  ├─ SideFenceLayer
│  ├─ FrontFenceLayer
│  └─ FenceCollisions
├─ BuildingOutputDisplay
├─ Collision
├─ InteractionArea
└─ CameraOccluder
```

`BuildingProductionYard` 负责围栏视觉、施工阶段、预览颜色、维修色调、围栏碰撞和收货区坐标。`BuildingOutputDisplay` 只负责产物模型、数量提示和收取交互。`BuildingInstance` 负责同步预览、施工、维修、淡入淡出和移除状态。围栏不是独立建筑，不参与建筑数量、维修队列、经济产出或独立存档。

## 围栏视觉

提供三套手绘 SVG 图集：

- `timber`：暖棕木板、绳结和略不规则木桩。
- `masonry`：低矮石基与木制横梁。
- `industrial`：深色石基、铁栏和铆钉。

每套图集包含正面和侧面方向，并包含地基、框架、半成品和完工四个施工阶段。围栏按院落边界格重复铺设；后侧围栏位于建筑后方，前侧围栏和收货区位于建筑前方，使用稳定的排序偏移保持遮挡关系。

预览时建筑和围栏统一变绿或变红。维修逾期时围栏降低饱和度，但破损标识只显示在主体附近。缺少图集时使用对应风格的简化色块围栏，并按资源路径只警告一次。

## 建造过程

围栏和建筑主体共享现有四阶段施工：

1. 地基：建筑地基与院落边界桩。
2. 框架：未完成横梁。
3. 半成品：围栏轮廓闭合但缺少部分细节。
4. 完工：完整围栏、阴影与装饰。

切帧继续使用现有 2 秒淡出淡入。从建筑放置成功开始，完整院落网格即标记为 `BUILDING`。地基阶段使用不可见边界阻挡，避免玩家进入施工区域；后续阶段启用对应围栏碰撞。

建造锤子、维修锤子和进度时钟始终按 `structure_footprint` 及主体偏移定位，不随院落外扩移动到角落。

## 阻挡与交互

不使用覆盖整个院落的巨大实体盒，以免遮挡院落内产物点击。

- 网格层：完整 3×3 或 4×4 占地标记为建筑，自动寻路不会进入。
- 物理层：四周围栏使用连续碰撞段，阻止玩家自由移动穿入。
- 主体层：建筑主体保留原始大小的碰撞、交互区域和摄像机遮挡区域。

围栏碰撞只使用玩家物理层，不进入产物点击层。建筑操作界面的交互区域仍围绕主体。产物继续使用独立的 `BuildingOutputPile` 鼠标触发机制。

## 产物收货区

所有产物统一放在围栏内侧、建筑正前方：

- 3×3 院落提供 6 个位置，两排排列。
- 4×4 院落提供 8 个位置，两排排列。
- 物品按 ID 稳定排序，刷新后不交换位置。
- 只有数量大于零的产物显示。
- 产物不会越过围栏、覆盖主体或彼此重叠。
- 悬停继续显示小字号、清晰的“名称 × 数量”。
- 点击成功后播放现有入库动画并移除模型。
- 背包已满时保留产物并显示失败反馈。

`BuildingOutputDisplay` 不再根据权威占地向外侧计算坐标，而是从院落组件取得前排收货区坐标。若产物类型超过显示位置，超出部分保留在库存与建筑界面中，但不创建重叠模型。

## 经济与维修兼容

扩大院落只改变空间布局，不改变经济平衡：

- 建造材料、配方、生产时间和存储容量保持不变。
- 维修费用按 `structure_footprint` 计算，不按院落面积计算。
- 队列、产物库存和维修状态仍属于主体建筑。
- 围栏破损色调跟随主体，不单独维修。

## 存档策略

新存档保存完整院落的 `occupied_cells`，围栏和产物位置加载后自动重建。顶层存档增加：

```json
"building_layout_version": 2
```

本次不迁移旧布局。存在网格/建筑快照但缺少版本 2 的旧存档会被明确拒绝，玩家需要开始新游戏。这样避免自动移动、覆盖或缩小旧建筑。调试面板的一键重置可用于快速建立兼容存档。

## 状态与数据流

1. 建筑目录读取院落配置并生成权威占地。
2. 建造预览按完整院落检查边界、水域和已有占用。
3. 放置成功后，`BuildingInstance` 配置主体偏移、主体物理体和院落组件。
4. 施工阶段变化同步围栏图集帧、透明度和碰撞。
5. `ProductionSystem.refresh_indicator` 同步主体活动、维修色调和产物库存。
6. `BuildingOutputDisplay` 请求院落槽位并生成可点击产物。
7. 拆除时主体、围栏、碰撞和派生产物一起释放，全部院落格恢复原状态。
8. 加载时先验证布局版本和完整占地，再恢复建筑；围栏不单独序列化。

## 验收标准

- 11 个生产建筑均有合法且唯一的院落配置。
- 尺寸严格符合已确认的 3×3 / 4×4 映射。
- 三种围栏图集和四个施工阶段均可加载。
- 预览、施工、完成、维修和拆除正确同步围栏。
- 完整院落不可寻路或物理穿越。
- 围栏不会拦截产物鼠标事件。
- 所有显示产物都位于围栏内部前方收货区。
- 点击产物正常入库并播放动画。
- 维修费用不因院落扩大而改变。
- 新存档可恢复院落、队列、产物和维修状态。
- 旧布局版本被明确拒绝，不产生部分恢复。
- 主场景可完成放置、施工、生产、收取、维修、保存和拆除流程。

## 测试策略

- 数据测试验证建筑清单、尺寸、主体尺寸、风格和槽位容量。
- 组件测试验证围栏段数量、图集资源、阶段切换、预览颜色和碰撞层。
- 建筑实例测试验证主体偏移、主体碰撞与院落碰撞相互独立。
- 产物测试验证槽位都在围栏内、排序稳定、交互不被围栏遮挡。
- 经济测试验证维修报价继续使用主体占地。
- 存档测试验证版本 2 往返、旧版本拒绝和失败原子性。
- 主场景集成测试验证完整生产院落生命周期。
