# 调试作物阶段推进与状态应用性能设计

## 目标

修复两个调试功能问题：

1. 按 `N` 时，每株仍在生长的作物直接进入下一个可见生长阶段，并立即刷新模型；正式日期和每日模拟保持不变。
2. 调试面板点击“应用”不再因同步广播无关事件、重建隐藏界面而卡住主线程。

## 已确认交互

- `N` 只在调试构建中生效。
- 每按一次 `N`，所有 `GROWING` 作物各推进到下一个可见阶段；最后一次推进会进入成熟状态。
- 成熟、休眠、枯萎以及暂停温室中的作物不推进。
- `N` 不改变日期、季节、时钟、日结游标、资源刷新或存档。
- HUD 显示本次推进株数和成熟株数；没有可推进作物时也给出提示。
- 调试面板的日期编辑是直接状态编辑，不代表正式跨日，不能广播 `day_changed` 或运行跳过日期的模拟。

## 根因

当前 `N` 复用了 `FarmingSystem.on_day_changed()`。该接口按一天的生长量增加进度；当增加后的进度没有跨过阶段阈值时，模型不变，而且没有反馈，因此用户看到的是“没有反应”。

`DebugStateEditor.apply()` 在每次成功应用后无条件广播等级、经验、金币、体力和日期事件。`day_changed` 会唤起正式日结消费者；金币、物品和蓝图事件还会让服务面板以及曾经打开过的建筑面板在同一个调用栈中反复销毁并重建控件。调试面板必须等整个同步信号链返回后才能恢复按钮，于是表现为卡死。

## 设计

### 1. 专用作物阶段推进 API

`FarmingSystem.debug_advance_growth_stage()` 遍历已种植地块，只处理可活动的 `GROWING` 作物。下一个进度阈值按作物的实际阶段数计算：

```text
next_progress = growth_days * (current_stage + 1) / (stage_count - 1)
```

到达最后阶段时同时设置生命周期为 `MATURE`。每个成功推进的地块立即调用现有视觉更新逻辑，并沿用 `crop_grew`、`crop_matured` 事件。接口返回推进数量和新成熟数量，供 `Main` 生成 HUD 提示。

该 API 不调用环境日切换逻辑，也不清除浇水状态，因为按 N 不是一天结算。

### 2. 调试应用只发布真实变化

`DebugStateEditor` 在修改前保存快照，成功后逐字段比较：

- 等级变化才发 `level_changed`，并发一次 `exp_gained(0)` 让经验条重读权威状态。
- 金币或体力变化才发对应事件。
- 物品继续只发准确的增减差值。
- 季节变化才发 `season_changed`。
- 永远不发 `day_changed`。

日期和时间标签由 `Main` 在应用成功后直接调用 HUD 的轻量刷新接口同步。生产、NPC、市场、每日模拟和资源系统的游标仍在事务内直接同步到目标日，避免下一次自然日结出现游标断层。

### 3. 合并昂贵界面刷新

服务面板收到金币、物品、蓝图等事件时，只安排一次下一帧刷新。面板不在可见树中时不重建；切换到服务页时现有入口会主动刷新。

建筑生产面板和状态面板采用相同规则：事件回调只安排刷新，隐藏时跳过；再次打开建筑时 `show_building()` 会读取最新权威状态。玩家在面板内直接执行的命令仍保留同步刷新，以维持点击后的即时反馈。

## 错误与边界

- 缺少农业系统时 N 返回失败且不消费输入。
- 阶段素材少于两个、成长天数无效或状态不允许推进的作物会被跳过。
- 重复应用完全相同的调试数据不发布任何游戏状态事件。
- 多个状态在一次应用中变化时，各轻量事件仍准确发布一次；所有昂贵 UI 刷新最多合并为下一帧一次。
- 调试状态校验或游标同步失败时维持现有回滚行为，不发布成功事件。

## 测试策略

- 真实 `FarmingSystem` 覆盖从种子到下一阶段、连续推进到成熟、视觉元数据更新、暂停/非生长作物跳过和浇水状态不变。
- `Main` 覆盖 N 不改变正式日期、调用专用 API并显示有作物/无作物两类提示。
- `DebugStateEditor` 覆盖相同快照零事件、字段变化的精确事件、日期编辑无 `day_changed`、日结模拟不运行。
- 服务面板和建筑面板覆盖事件回调不做同步重建、同帧多事件合并、隐藏状态跳过以及重新打开时刷新。
- 最后运行调试、农业、经济 UI、建筑 UI 和主玩法回归套件。

## 非目标

- 不改变自然时间流逝触发的正式每日模拟。
- 不修改作物正常浇水成长倍率。
- 不把调试面板应用改造成分帧事务。
- 不重构所有经济 UI 的渲染架构。
