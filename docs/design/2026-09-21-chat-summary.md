# 聊天摘要与单轮行为提取

原聊天模型输入已经有 6 条消息、1800 字的历史限制，因此尚不能把重复回复认定为无限增长的 context 导致。原实现直接丢弃窗口外的进展，没有聊天摘要；原行为提取则读取 12 条历史消息。这次修改针对历史进展遗失和反复提取旧安排的问题，不声称仅靠摘要就能消除模型重复。

## 聊天上下文

- 当前角色人设、当前角色和重点 NPC 名单、玩家名称及简短对话规则。
- 最多 800 字的滚动摘要，仅保留事实、话题进展、偏好、已确认／取消／待确认的安排和未解决问题。禁止复用长台词、动作模板，不把口头约定当作已经执行。
- 最近最多 8 条原始消息，原文总量上限 6000 字；长回复会减少条数，保证当前玩家消息完整。按消息写入顺序读取，不受调试修改游戏时间影响。
- 窗口外的新消息与旧摘要增量合并，由同一个本地聊天模型执行独立 `summarize_chat` 调用，然后生成本轮聊天回复。正常持续聊天每轮压缩刚移出的消息；旧存档的积压按最多 32 条、目标 12000 字一批逐轮追赶，单条超长消息仍完整处理。
- 摘要写入现有 `history_heads`，原始消息不删除。私聊、群聊、会话、重置代次相互隔离；检查点导入导出保留摘要及覆盖位置。
- 失败保留旧摘要和候选消息，下一轮重试，原始窗口不会因失败扩张。取消、重置、存档恢复造成来源变化、并发较新摘要均会阻止旧结果覆盖。

调试窗口调用列表增加“聊天摘要”。`chat.summary_updated` 包含摘要及覆盖消息 ID；`chat.summary_failed` 标明重试；`chat.context_window` 显示保留消息和提取范围。模型 Input 中可直接查看 `conversation_summary`。

## 行为提取

提取模型只收到当前玩家消息和当前 NPC 回复，二者均带发言者标记。摘要、旧提议和群内其他 NPC 回复都不进入提取调用。双方证据均必须来自这一轮。

玩家说“好”时，聊天模型根据自己的历史上下文自然确认“好，我们去南湖散步”，提取器从这句当前确认取得 `lake + walk`。如果当前 NPC 只回复“那就出发”，缺少地点／行为，则不从旧历史补全。旧约定不会单凭仍在摘要中而被再次抽取。

## 回复正文显示修正

实际记录表明本地模型会在回复正文前生成“角色背景／你是／当前场景”的 Markdown 说明；这些内容来自模型回复，并非对话框拼接了请求。服务端只移除已识别的前置说明块，保留普通正文和普通标题，分片输出时也先判断前缀，避免说明闪入对话框。已知 `speaker/text` 包装会解包。原始模型输出完整保留在 `provider.output`，历史回复在重新送入聊天或摘要时进行同样的正文处理，避免继续模仿旧格式。

独立聊天的最终台词也不再追加提取失败和行动结果说明；这些信息继续保留在行动跟踪与日志中。回归测试覆盖逐字分片、原始输出留存、普通标题保留、历史消息处理与最终台词一致性。

## 验证范围

自动测试覆盖 18 轮连续 HTTP 聊天、原始窗口和摘要限制、按写入顺序读取、增量覆盖不重复、长回复进入摘要、摘要失败重试、取消／重置、并发旧结果、存档恢复、私聊／群聊隔离。模拟模型的实际 HTTP 请求验证摘要只进入聊天，提取请求仅有最新两条消息。

本次保持 Agent Service 和 Ollama 停止，没有进行真实本地模型的长对话效果验证。需下次启动服务后观察重复回复是否改善；本次证据证明上下文维护和提取边界的实现。
