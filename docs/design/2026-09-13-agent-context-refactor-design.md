# NPC Agent 按需上下文与持久记忆重构设计

日期：2026-09-13。状态：设计草案，尚未实施。已补充定时/事件驱动 Agent Loop、短期目标、行动执行反馈和循环内自动压缩。

范围：正式 `scenes/farm3d/main.tscn` 的 NPC Agent。沿用 `feature/3d-farm-preview`、既有 Godot 领域系统和 TypeScript Agent Service。本轮只确定设计，不修改运行时代码。

## 1. 目标与关键决定

每次模型调用以四块固定头部开始：GameEnv、身份与性格/目标、准确的当前资源、最近 15 条事件及更早事件摘要。头部之后独立加入与当前情境相关的持久记忆、本轮输入，以及模型在本轮主动查询获得的信息。

市场、地图、建筑、任务、工作、社会活动、其他角色与关系、探索知识和情报不再随初始请求全量传输，也不自动加入初始 prompt。模型通过能力目录知道这些玩法存在，自行决定查询什么。

关键决定：

1. 四块头部结构固定，资源和事件动态更新；“固定”不意味着旧数据永久不变。
2. Godot 继续拥有资源和世界状态的唯一写入权。服务端持久化资源的版本化镜像，不产生第二本账。
3. 事件窗口、历史摘要、长期记忆分开存储和使用。窗口保证连续性，摘要保留经历脉络，记忆支持相关性检索。
4. 读取结果进入本轮工作上下文。跨轮只检索相关记忆，不把历次探索结果自动全部带回来。
5. 读取改为 Godot 按领域现场查询，不依赖预先构建整个世界快照。每份观察记录时间、版本和可见范围。
6. 工具定义也按需加载。初始只提供简短领域目录和少量基础工具；打开领域后提供该领域的具体工具与规则。
7. 对话、自主决策、协商使用同一个上下文构建器，不再维护两套裁剪逻辑。三者仅在当前输入、行为规则和预算上不同。
8. 一次有效唤醒创建一个 Agent Loop：构建上下文、按需读取、形成有限行动批次、由 Godot 自动执行、记录结果和重建上下文材料。下一次模型推理必须由新的有效事件或定时器触发。
9. 对话和世界事件可以促成短期目标。目标通过类型化工具持久化，行动仍通过既有领域工具执行；目标记录不等于承诺履行或世界状态改变。
10. Loop 工作上下文达到配置阈值时自动压缩；压缩不清零读取次数、行动数、费用或重试预算。

## 2. 当前实现与必须替换的位置

| 当前入口 | 现状 | 重构方向 |
|---|---|---|
| `scripts/ai_agent/agent_runtime.gd::_build_request` | 构建资源、全部市场、农田、建筑、人物、工作和知识等快照 | 只构建头部输入、资源版本、事件同步水位和读取会话 |
| `agent_context_projection.gd` | 公共事件、人物和个人事件多路注入 | 改为统一的、按观察者授权的事件输入；人物与领域状态改为工具查询 |
| `services/agent-service/src/agents.ts::buildContext` | 拼装整个游戏快照和记忆 | 只组装固定头部、相关记忆及本轮输入 |
| `provider.ts::buildDialogueContext` | 另行裁剪；记忆直接取前 6 条 | 删除专用裁剪，统一预算和相关记忆检索 |
| `tool_contracts.ts::executeReadTool` | 从已传入服务端的快照读取 | 抽为异步读取接口，查询 Godot 或本地记忆库 |
| `app.ts::decisionContext` | 8 条长期记忆 + 8 条近期事件 | 15 条统一事件、历史摘要、独立的相关记忆检索 |
| `memory.ts` | 事件评分、满 20 条压缩；现有版本升级可能清表 | 增量事件接入、分层摘要、结构化记忆、无损迁移 |

现有 `known_actors` 排除自己，精简对话却从中查询自己的 `current_activity`。新设计中自身活动通过 `inspect_current_activity` 从活动/项目执行器读取，避免延续这个空字段。

## 3. 模型输入结构

```text
system
  GameEnv：静态玩法介绍 + 能力目录 + 通用事实/行动规则
user
  identity：身份、Soul、当前职业、目标
  resources：带版本和时间的当前资源
  experience：older_summary + recent_events[最多15条]
  relevant_memories：从持久库检索的相关记忆
  turn：触发类型、当前时间、玩家原话或触发事件引用
assistant / tool（只在本轮需要时逐步追加）
  领域发现、查询结果、补充记忆、失败反馈
```

这是逻辑上的四块固定头部：GameEnv、identity、resources、experience。`relevant_memories` 为按需检索的动态附件，不是第五个全量知识仓库；`turn` 是本轮必要输入。固定规则和可变数据分开，便于诊断体积和复用固定前缀。

初始上下文中明确不再出现 `market_summary`、`market_view`、`known_actors`、整块 `living_world`、全部建筑/角色/农田/知识列表，以及重复的 `global_public_events` 和 `own_event_delta`。

### 3.1 GameEnv

独立静态配置，建议 `data/agents/game_env.json`，带 `version`。它介绍玩法和获取信息的方式，不列当前世界对象。

示例文案：

> 你生活在一个会随时间和季节变化的农庄村落。你可以依照自己的性格与目标经营农田、买卖物品、租用或建设生产设施，接受或发布委托，与其他居民协商工作、合作和交易，也可以探索区域、调查与分享情报、参加社会活动。资源、时间和承诺都有真实约束；提出计划不等于已经完成。你只能依据自己的资源、经历、记忆和实际查询所得信息作决定。市场、建筑、任务、人物、环境和探索信息都可以通过领域工具逐步了解。先判断当前缺少什么信息，再查询相应领域；没有需要时可以直接交流或等待。价格、库存、人员位置和任务状态会变化，重要行动前查询当前事实。

配套简短能力目录：`self`、`map`、`farm`、`market`、`buildings`、`tasks`、`goals`、`social`、`actors`、`knowledge`、`environment`、`memory`。每项只有一句用途和入口，不含实例数据、长参数表或整段领域规则。

公共协调者使用同一静态游戏介绍的公共角色版本和单独的公共能力目录；不继承 NPC 的私人读取权限。

### 3.2 身份、人格和目标

保留当前 `agent_id`、`display_name`、`active_role`、`goals`、Soul 的 `traits`、`values`、`speech_style`、`risk_tolerance`。

职业目标和人格为必带内容，不能为减少 token 被摘要或截掉。给现有目标 ID 配置简短、确定性的含义说明，让模型知道目标代表的实际偏好。目标含义只维护一份。

区分职业长期目标、短期目标和当前项目：职业长期目标在头部；短期目标由对话/事件促成并持久化；项目负责已接受行动的确定性执行。后两者通过事件/相关记忆得到线索，再查询目标/任务工具取得现状。短期目标和当前项目不能被 LLM 总结成新的职业授权，详见第 14 节。

### 3.3 当前资源：完整、版本化、可核对

保留当前全部字段：金币、背包、储备目标、生产配方、出售目标、上次模拟日期、投资计划标记。增加 `resource_revision`、`observed_game_minute`、`checkpoint_id` 等一致性元数据。

金币和背包定义为当前可自由支配的金额与物品。项目/合同已经托管的资产不重复算入可花资源；托管明细通过任务工具查询。生产配方保留当前列表，完整配方参数通过领域工具读取。

同步策略：

- 每次决策前，在 Godot 主线程同一采样点获取完整资源并随请求提交；这是进入模型前的必要步骤。
- 交易、生产、委托托管/退款、配送、每日结算等实际提交后，发布资源版本变化并进入可靠待发送队列。
- 定期核对建议默认每 60 游戏分钟一次，按版本/哈希批量同步有变化的主体，不调用 LLM；读档、重连立即全量核对。
- 资源仍随现有 `farm_session.gd` 的 `npc_economy` 保存到游戏存档；服务端保存最新镜像用于恢复核对和追踪。
- 断线时不通过记忆或资源 delta 推算“当前余额”。下一次成功请求使用 Godot 完整状态覆盖旧镜像。
- LLM 的文字、计划、读取结果和长期记忆都不能直接改写资源字段。

同一会话代际中拒绝倒退的版本。读旧档会创建新代际，并从匹配的存档检查点恢复，不拿未来镜像覆盖旧档。读取期间如果发现自身资源版本变化，下一模型轮替换资源头部；保留旧观察的时间标签，不把两次余额相加。

### 3.4 最近 15 条事件与历史摘要

建立每个 Agent 独立的统一经历时间线。包括：决策、完整对话交换、动作状态变化、实际资源结算、任务/合同变化、对该 NPC 可见的社会与环境事件、有效发现。

每条至少包含 `event_id`、`source`、`source_event_id`、`agent_id`、`episode_id`、`kind`、`game_minute`、单调 `agent_sequence`、相关实体、事实状态和紧凑内容。Godot 事实与服务端决策用 `request_id/decision_id/action_id/correlation_id` 建立因果关系。

- 最近窗口按持久接入序号选最新 15 条，按序展示；游戏时间用于叙事，同分钟和迟到事件不会破坏水位。迟到事件保留原发生时间并标记迟到。
- 一次玩家输入与 NPC 回答构成一个对话事件，保留原文。当前尚未完成的玩家输入放在 `turn`，不重复塞进历史。
- 决策意图、执行中、成功、失败是不同事实。通过同一 episode 关联，不将“决定买”变成“已经买到”。
- 原始领域事件可靠保存。进入 Agent 时间线前合并高频、重复通知，例如逐帧移动和无变化时钟 tick；保留移动开始/到达/失败等有意义状态。
- 公共事件按授权接入同一时间线，不再从公共列表和私人 delta 重复注入。
- 最近 15 条之外的经历进入 `older_summary`，窗口和摘要用 `covered_through_sequence` 划界，避免重叠和遗漏。

摘要采用持久化分段摘要 + 有预算的滚动概述。摘要覆盖事件、角色、因果、承诺状态、结果和未解决线索，并保留来源 ID。历史摘要进一步归并时保留覆盖区间，原始事件和分段摘要仍可查询。

摘要更新异步执行。窗口刚溢出而模型摘要未完成时，使用程序生成的紧凑事实段覆盖新增区间，并替换同区间的旧版本；禁止把未摘要部分直接丢掉。高流量时可按类型/实体合并，完整事实仍在原始库。

摘要是经历，不是当前世界状态：旧价格、旧余额、旧合同状态必须带时间，不能覆盖资源头部或新工具观察。长对话/巨大动作 payload 的 prompt 表示可用保真摘录加原文引用，原文不可删除，当前玩家输入保留完整。

## 4. 持久记忆：从事实提取，按当前需要检索

### 4.1 事件摘要与长期记忆的职责

| 数据 | 回答的问题 | 生命周期 |
|---|---|---|
| 最近 15 条事件 | 刚刚发生了什么？ | 滚动窗口，原始记录持久保存 |
| 更早事件摘要 | 我之前经历了什么、事情怎样发展？ | 分段和滚动摘要，按水位更新 |
| 长期记忆 | 当前这句话/目标值得回忆哪些重要事实？ | 独立事实条目，按相关性召回 |
| 本轮工具观察 | 我刚查询到了什么？ | 本轮工作上下文；有价值部分转为观察事件/记忆 |

同一事实可以同时有摘要与记忆，但最终上下文按来源去重。长期记忆不直接复用一大段历史摘要，摘要也不能成为没有原始来源的“事实”。

### 4.2 提取链路

Godot 已提交且对该 NPC 可见的领域事件，以及服务端持久化的对话/决策事件，进入统一事件库。事件接入与记忆提取任务同时可靠落盘，服务离线时由 Godot 持久 outbox 重试，按来源 ID 去重。

先由规则筛选重要候选，再异步让模型提取结构化记忆；不再等满 20 条重要事件才具备记忆，也不只在上报动作结果时启动处理。合同接受、违约、重大损失、重要发现、玩家明确偏好等事件可单独触发；一般事件短批处理。

重要候选在模型提取尚未完成时，也可通过确定性的事实索引检索，避免下一次对话“刚发生却忘记”。提取失败保留任务和原文重试；不阻塞玩家对话。

记忆字段：`memory_id`、`agent_id`、`session_id`、`timeline_id`、`type`、`statement`、`entity_ids`、`tags`、`importance`、`confidence`、`source_event_ids`、`observed_at`、`valid_from`、`valid_until`、`status`、`supersedes`。

记忆类型覆盖关系经历、人物偏好、承诺、成功/失败经验、观察发现和未解决事项。模型只返回提取建议，服务端校验来源、可见性、时间与结构后落库。NPC 的打算记录为意图；玩家口述记录为“玩家曾说”；听闻、推测和实际完成不能互换。模型推理 trace 不作为事实记忆来源。

任务完成/取消后，旧承诺变为已完成/失效并关联新证据；不删除曾经承诺的经历。市场价格和人物位置一般留作带时效的观察，不当作永久事实。角色设定仍以 profile 为准，记忆不自行改写人格。

### 4.3 每轮相关记忆检索

每次对话必须执行检索；自主决策和事件唤醒复用同一路径。

1. 从当前玩家输入、交谈对象、职业目标、触发事件和最近经历中的实体构建查询，不扫描全世界状态来构建查询。
2. 在该 Agent、该存档时间线内按实体 ID、标签、关键词和近期性召回候选；承诺/未解决事项通过独立小索引召回。
3. 按主题/实体相关性、未解决状态、重要度、可信度和时效排序；对已覆盖于最近事件或摘要中的来源去重。
4. 选择少量互补条目，建议最多 6 条且不超过 800 token。空相关结果就返回空数组，不用不相关的老记忆填满。
5. 一条相关承诺只携带 ID、简述、最后已知状态和时间；需要采取行动时用任务工具核实当前版本和条款。

首版采用 SQLite 结构化索引 + 中文可用的关键词/字符 n-gram 索引。现有默认 FTS5 对连续中文文本不能直接假定有良好分词效果，需要中文检索用例验证。预留 embedding 检索适配器，是否引入由召回评测决定，不把新远程 embedding 服务作为首版依赖。

提供 `recall_memory(query, entity_ids, types, limit)` 和 `inspect_event(event_id)` 供模型进一步回忆。它们仍执行同一作用域/可见性检查，不支持任意数据库查询。

## 5. 按需工具与自主发现

### 5.1 初始工具菜单

初始仅装载 `discover_tools`、`inspect_self_resources`、`recall_memory` 和必要的基础动作（例如 `speak`、`wait`；也可直接返回无动作回复）。身份与静态目录告诉模型可以主动了解哪些领域。

`discover_tools(domains, purpose)` 不读取世界实例，返回所选领域的简短玩法/规则，并使下一轮模型请求装载该领域授权工具的 JSON Schema。`purpose` 是简短信息需要，不要求模型输出详细推理。

服务端始终持有完整能力目录；模型只能发现“当前角色授权 ∩ Godot 当前能力 ∩ 对话/调度模式允许”的工具。发现工具不能提升权限，也不自动执行命令。不要用接受任意字符串和参数的通用执行器替代类型化动作校验。

目录发现与具体查询均属于只读阶段；发现产生的工具定义只在 `tools` 菜单出现，tool 正文不重复整套 schema。已加载领域在本轮复用，按预算逐出不相关定义；下一次决策从基础菜单重新开始。

### 5.2 领域读取目录（拟定接口）

| 领域 | 发现/列表工具 | 详情/后续工具 |
|---|---|---|
| 自己 | `inspect_current_activity` | `inspect_self_resources` |
| 地图 | `inspect_map(scope, cursor)` | `inspect_region(region_id)` |
| 农业 | `inspect_farm_plots(filter, cursor)` | `inspect_crop_options(filter, cursor)` |
| 市场 | `search_market(query, category, cursor)` | `inspect_market_item`、`compare_market_items`、`inspect_market_depth`、`inspect_price_history` |
| 建筑 | `search_buildings(type, region_id, service, cursor)` | `inspect_building(building_id)`、`inspect_recipe(recipe_id)`、`inspect_legal_sites` |
| 任务与工作 | `list_tasks(scope, status, cursor)` | `inspect_project`、`inspect_commission`、`inspect_work_contract`、`inspect_delivery`、`inspect_joint_project`、`inspect_training` |
| 短期目标 | `list_short_term_goals(status, cursor)` | `inspect_short_term_goal(goal_id)`；通过目标动作工具采纳、修改或放弃 |
| 社会活动 | `list_social_activities(filter, cursor)` | `inspect_social_activity(activity_id)` |
| 人物与关系 | `search_actors(query, region_id, cursor)` | `inspect_actor(actor_id)`、`inspect_relationship(actor_id)`、`list_interactions`、`inspect_trade_offer`、`inspect_agreement`、`inspect_role_option` |
| 知识与情报 | `search_knowledge(query, kind, cursor)` | `inspect_discovery`、`list_intelligence_offers`、`inspect_intelligence_offer`、`inspect_investigation` |
| 环境 | `inspect_environment(topic)` | 天气预报、道路/维修、运输、社会指标的按主题详情 |
| 记忆 | `recall_memory` | `inspect_event`、`inspect_history_segment` |

具体命名实施时与既有工具协调；验收要求是所有从初始 context 移出的能力都有“无 ID 可发现 → 有 ID 可查询 → 有权限可行动”的完整路径。不能只有详情工具却没有找到对象 ID 的入口。

列表默认最多 5 项，允许上限 10 项，明确 `next_cursor/has_more`，不把完整历史藏在某个对象的子数组里。详情按用途拆出配方、队列、履约记录等分页数据。查询必须明确区分未知、无权限、没有记录、暂时不可用和已过期。

### 5.3 工具观察如何进入上下文

结果统一携带 `observation_id`、`domain`、`observed_game_minute`、`domain_revision`、来源、可见范围、数据、分页信息和失效提示。

工具响应直接作为本轮 `tool` 消息追加，后续模型轮能引用。WorkingContext 只存结果引用和版本索引，不在 user JSON 再复制一遍相同结果。相同查询复用仍有效结果；刷新后标明替代哪次观察。

本轮结束后，普通临时结果从模型上下文退出；稳定且重要的发现按事件/记忆链路持久化。价格等短期观察可留带时效的审计记录，下一轮不自动带回。长期记忆可以提示“以前知道这里有风车”，当前租费/是否开放仍需查询。

原始读取回执可缓存用于同次请求重试和调试；它不等同于世界知识库。需要控制增长时，删除旧回合成对的 assistant/tool 消息，再插入有来源的紧凑观察记录；不得破坏 tool_call_id 配对，当前承诺条款和最终动作所依据的数据不能只剩模糊摘要。

### 5.4 自主查询示例

“想赚一笔稳定收入”：从职业目标和现有资源判断缺少机会信息 → 发现市场/任务工具 → 查询与库存相关的商品和开放委托 → 需要加工时才发现建筑工具 → 查真实配方、租费和时间 → 选择方案或放弃。

“你上次答应送的面包呢”：自动召回这次承诺及近期配送事件 → 如状态不足，发现任务工具并查询该任务 ID → 按实际状态回答。不会顺带加载全部市场和地图。

“你好”：固定头部和相关记忆足够时直接回复，工具调用为零。不要求每轮探索，也不预写必须遍历的玩法流程。

查询地图不等于人物已经旅行；未知实地内容仍需授权的移动/调查动作获得。公开地点与私有情报按现有领域权限返回，不能通过工具发现绕过付费/分享规则。

## 6. Godot 与服务端的按需读取通道

仅仅从 prompt 删除字段、仍在每次 `_build_request` 构建完整快照，不能作为最终实现。

建议在现有 SSE 决策通道增加异步读取往返：

```text
Godot ── 精简决策请求 ──> Agent Service ── 头部/记忆/工具 ──> LLM
Godot <── SSE read.request ── Agent Service <── 类型化工具调用 ── LLM
Godot ── POST read.result ──> Agent Service ── tool 观察结果 ──> LLM
Godot <── 最终动作意图 ── Agent Service <── 决策/回复 ── LLM
```

新增 `WorldReadBroker` 管理服务端等待中的调用；Godot 的 `AgentWorldQueryRouter` 按领域分发主线程只读查询。记忆和工具目录查询直接在服务端完成，不绕行 Godot。

每次查询绑定 `session_id + timeline_id + session_epoch + request_id + agent_id + read_id` 和参数摘要。结果只接受对应连接、已发起工具和当前有效会话；重复返回幂等。读档、关闭对话、退出游戏和请求取消清理等待项，迟到结果不可进入另一轮。

Godot 查询处理与网络节点在暂停时仍可运行；不得等待游戏恢复才返回对话需要的只读结果。单次查询超时建议 5 秒，产生 `temporarily_unavailable` 工具结果供模型降级，不伪造空世界。查询不得触发结算、价格更新或随机探索；例如预报应读取预先生成的数据，不能因为读取而推进环境。

不冻结整个游戏等待模型。单次查询在同一逻辑采样点读取对应领域；有依赖的报价/配方/库存查询提供同批次读取或共同版本标记。不同时间的观察不声称是全局一致快照。

价格、资源、合同、任务等改变后必须由 Godot 在执行前复核。现有 `expected_revision` 与新观察版本的关系需两端显式定义，禁止服务端偷偷改写 revision 来绕过旧校验：请求携带初始执行 revision，刷新返回新的观察 revision，最终意图绑定明确的已观察 revision；执行器继续检查幂等、权限、实时资源、条款版本和费用上限。版本失效返回明确错误，重新读取/规划，不自动重复已完成动作。

决策端点升级协议 v3，旧协议显式不兼容，不保留“完整快照版”决策回退。保留命令自身 `tool_version=1` 与既有领域执行器；传输包版本和动作字段由两端同步升级。旧非流式决策端点在 v3 返回明确的需升级流式客户端错误，避免缺少反向读取通道的半功能实现。

## 7. 上下文和工具预算

以下是首轮实施的可配置起点，需要用真实 trace 验证后调整，不是当前测量结果。

| 内容 | 建议预算 |
|---|---|
| GameEnv + 静态目录 | 约 600 token |
| 身份与人格/目标 | 约 400 token；必带，不截断 |
| 当前资源 | 全量必带，实际计量，不截断数量或字段 |
| 最近 15 条事件的 prompt 表示 | 目标约 1,800 token；长原文保存在可查事件库 |
| 更早事件滚动摘要 | 约 600 token |
| 自动检索相关记忆 | 最多 6 条 / 800 token |
| 初始工具 schema | 目标不超过 800 token |
| 单个列表/详情观察 | 默认目标 800 token，复杂条款按需分页/放宽 |
| 本轮工具结果累计 | 默认 6,000 token；达到后优先去重和收束 |

初始请求目标为 3,000～5,000 token 加必要资源/输入超额，具体以实际 provider 输入测量；不为达标删掉人格、目标、真实资源或当前玩家问题。所有 `messages`、工具定义和领域规则均计入统计，不能只计算 context JSON。

普通决策与复杂对话最多 6 个读取轮次、12 次读取调用作为起点，发现工具也计入；单轮最多 4 次独立读取，查询同一变化领域尽量合批。问候不读、简单问答争取 0～2 轮，但不能通过固定两轮上限阻断“发现→列表→详情”的必要路径。

预算剩余通过工具元信息简短告知。耗尽时明确本轮未能获取的事实，选择已有充分依据的动作、等待或回复；不猜测未知 ID、价格或结果。按真实需要安排后续正常调度，不为耗尽预算立刻自激发无限决策。

模型请求沿用 Provider 并发和玩家对话优先策略。等待 Godot 工具结果时不占远程 Provider 槽位。读取往返、自动记忆检索不计新的“NPC 自主规划次数”，但所有实际 LLM 轮次以及摘要/记忆提取仍计 token 和费用预算；后台记忆任务低优先级并可推迟。

## 8. 持久化、恢复和事件可靠性

建议在现有 SQLite 增量增加：`agent_events`（或迁移既有 events）、`event_delivery_state`、`history_segments`、`history_heads`、`memories`、`memory_jobs`、`resource_snapshots`。按会话/时间线/Agent 建索引与唯一约束。

Godot 世界事件日志与服务端 Agent 经历库职责不同：前者记录权威世界事实，后者记录某 NPC 已被授权感知的经历，加上服务端决策/对话。现有游戏存档会压缩世界历史，因此不能假定读档后可以从 Godot 完整重建所有旧对话。

事件传输使用持久 outbox、批量接入、连续序号确认水位。只在服务端持久化成功后确认传输；与“本轮决策是否成功”分离，模型失败不应让已经发生的事实丢失。离线期间继续落盘，重连补传。

每次决策携带事件水位。服务端需要先接入到该水位再构建 15 条窗口，不能静默拿旧窗口调用模型；通常通过决策前同步或携带尚未确认的紧凑事件批次解决，超时返回可重试的上下文未就绪状态。

多源经历的持久接入序号由服务端分配；来源幂等键包含会话、时间线、Agent、来源系统和来源事件 ID，同一公共事件投影给不同 Agent 不能彼此冲突。

读取工具回执和决策意图保留请求关联。读取发现只有在确实返回给该 Agent 时才成为该 Agent 的观察；系统拥有该信息不代表 Agent 已经知道。传输取消后的观察可以留审计，但不冒充已被模型读取的记忆。

检查点继续与游戏存档 SHA-256 绑定；同时保存资源版本、事件接入/确认水位、摘要覆盖水位、记忆版本及待处理队列。存档时对“世界事件水位 + 服务端决策水位”建立一致边界，边界之后的事件不能混入该检查点。

读旧档恢复匹配检查点并切换运行代际，未匹配的未来记忆不得自动带入。缺失记忆 sidecar 时允许从游戏已保存的 outbox/事件和资源恢复可恢复部分，并明确记录缺口；不声称已恢复不存在的旧对话。版本升级采用事务迁移和备份，禁止沿用当前不匹配即清空记忆表的做法。

首次迁移把既有 decision/dialogue/outcome 记录和长期记忆保留为 legacy 来源；无法补全的实体和时间保持未知，不凭空生成。旧记忆来源不足时降低可信度，仍可查询历史。

## 9. 模块职责与实施顺序

| 模块 | 职责 |
|---|---|
| `AgentContextBuilder`（TS） | 唯一初始上下文构建、字段白名单和预算 |
| `AgentExperienceStore`（TS） | 统一事件接入、水位、15 条窗口、历史段 |
| `HistorySummarizer`（TS） | 分段摘要和滚动概述；带覆盖水位 |
| `AgentMemoryService`（TS） | 重要事实候选、异步提取、版本变更和相关检索 |
| `WorkingContext`（TS） | 本轮观察引用、去重、失效、消息预算 |
| `ToolCatalog` / `WorldReadBroker`（TS） | 领域工具发现、权限交集、按需装载、读取往返 |
| `AgentResourceProjection`（Godot） | 同采样点资源快照、版本与镜像同步 |
| `AgentExperienceOutbox`（Godot） | 可见事件投递、确认、恢复 |
| `AgentWorldQueryRouter`（Godot） | 各领域类型化查询，不复制领域业务逻辑 |

实施分四步，各步保持可验证，正式切换前不启用半套上下文：

1. **经历与持久化基础**：事件类型/来源映射、outbox、无损数据库迁移、资源版本、摘要与记忆检索；完成旧数据迁移验证。
2. **按需查询基础**：能力目录、类型化领域读接口、SSE 往返、分页/版本/暂停和取消；补齐每个原 context 字段的发现入口。
3. **统一上下文切换**：协议 v3、四块头部、相关记忆、工作上下文、动态工具 schema；移除全量构建和旧对话裁剪。
4. **集成与真实调用验收**：经营、项目、配送、情报和社交案例，评测 token、工具轮次、记忆相关性与动作正确性；完成公共协调者的隔离适配。

公共协调者复用基础设施，但固定资源代表公共预算，目标为公共目标，事件/记忆/查询限于授权公共事实。已有公共计划、预算约束和公共行动规则必须可被其领域工具完整发现，不能因为普通 NPC 缩减而丢失公共约束。

## 10. 验收标准

### 初始上下文与发现能力

- 捕获真实 Provider 第一轮输入：只有四块头部、相关记忆、本轮输入和基础工具；没有全部市场、地图对象、人物、合同/项目或知识数据。
- Godot 初始请求构建中不再调用整个市场/全部建筑/全部人物/整块生活世界的快照组装函数。懒加载由调用计数验证。
- 问候零工具；基于库存的盈利计划能自行发现市场→任务/建筑→报价；不知道 ID 时能从列表找到详情。
- 每项从旧 context 移出的可决策信息都有授权查询入口；复杂工作/项目的条款、能力、错误和修正路径没有缺口。
- 去掉旧两轮限制后仍受明确的调用数、上下文和时延预算约束，不重复查询同一未变化信息。

### 资源与执行

- 买卖、生产、托管、退款、每日结算、读档、断线重连后，模型头部资源与 Godot 权威状态完全一致。
- 等待 LLM 期间资源/价格/任务改变，旧观察可识别，执行器按当前事实复核；重复请求不会重复扣款。
- 查询不推进模拟、不生成免费调查结果；游戏暂停时的对话读取正常完成。

### 事件、摘要与记忆

- 输入 0、15、16、100 条及同分钟/乱序/重复事件，窗口最多且在足量时恰好 15 条；剩余摘要覆盖区间明确，无静默缺口。
- 模型摘要失败、服务重启和断线期间不丢原始经历；历史重放去重，不重复学习同一事实。
- 玩家承诺、实际完成、失败与传闻保持事实状态；重要发现和合同事件无需等 20 条即可被下一次相关对话召回。
- 已有 8 条长期记忆时，新近对话仍出现在 15 条事件窗口；旧记忆不能挤掉最近聊天。
- 用中文问题测相同实体别名、语义近似表达、无关记忆排除、过期状态、已完成承诺、跨 NPC 和跨存档隔离。
- 读回旧档不包含未来记忆；数据库迁移和匹配检查点恢复不删除已有记忆；缺失 sidecar 明确记录缺口。

### 测量

- 按身份、资源、事件、摘要、检索记忆、工具定义、工具结果分别记录 token/字节、条数和耗时；不记录密钥。
- 对同一组旧版场景建立基线，普通初始请求以减少至少 60% 总输入 token 为目标，同时报告资源/玩家长输入造成的例外，不通过漏字段达标。
- 同时报告总轮次、整次输入 token、总延迟、工具成功率、任务完成率和记忆召回质量；不能只展示第一轮变小而掩盖总调用成本上升。

## 11. 设计边界

本设计确定“短头部 + 自主读取 + 相关记忆”的架构，不重写经济、NPC 项目执行、角色人格或存档主体。新工具名称和 token 数值是实施起点；原始人格/目标、准确资源、15 条经历、越界历史摘要、持久重要记忆和按需发现能力是必须满足的需求。

## 12. Agent Loop：一次唤醒，一次有限决策过程

本节至第 18 节补充 2026-09-13 的后续需求：定时/事件驱动、对话促成短期目标、读取后调用行动工具、执行结果驱动下一轮，以及 Loop 内自动压缩。

### 12.1 术语和边界

- **Trigger（触发）**：定时到期、玩家对话、授权世界事件或行动反馈。先进入触发队列，通过调度条件后才创建 Loop。
- **Agent Loop**：一次被调度的唤醒，包含上下文构建、若干模型/工具轮次、最多一个最终行动批次及其执行结果归档。允许零行动结束。
- **Model Round（模型轮次）**：一次远程模型请求。一个 Loop 可以有多轮查询、读取和最终决策。
- **Action Batch（行动批次）**：本 Loop 最后提交的一组有序行动工具调用。默认普通 Loop 最多 3 个，对话 Loop 最多 1 个，配置可调整。
- **Execution（执行）**：Godot 执行器负责实际走路、操作、资源扣除和状态更新。执行结果是事件来源，不依赖模型叙述来确认。
- **Next Loop（下一轮）**：行动反馈形成有效触发，或其他事件/定时器到来后，新建上下文与新的 Loop ID。不能把新一批行动伪装成原 Loop 的无限延伸。

一次 Loop 只能提交一次合法行动批次。提交前的有限格式纠错不算第二批；提交后若想根据执行结果改变计划，需要下一次 Loop。已接受的批次内部续行、生产订单或项目执行不需要再调用模型。

### 12.2 生命周期

```text
触发队列（定时 / 对话 / 世界事件 / 行动反馈）
  → 调度准入与合并
  → BUILD_CONTEXT：同步资源/事件，构建头部和相关记忆
  → REASON：调用模型
      → READ_TOOLS：发现工具或读取领域 → 追加观察 → REASON
      → COMPACT：超过阈值时压缩工作上下文 → REASON
      → FINALIZE：形成零行动回复，或最终有限行动批次
  → VALIDATE：整批结构/权限校验，再按实际执行时的领域前置条件核验
  → EXECUTE：即时完成，或交给异步游戏执行器
  → WAIT_EXECUTION：不保持模型请求/远程槽位，等待实际回执
  → RECORD_AND_REFRESH：记录结果、更新资源和经历、刷新上下文材料
  → CLOSED
      → 有效反馈触发入队 → 下一 Loop
      → 无有效触发 → 等待事件或定时器
```

`READ_TOOLS` 和 `COMPACT` 只在行动提交前发生。`WAIT_EXECUTION` 是游戏端的持久执行状态，不是一个一直挂着的 Provider HTTP 请求；最终意图交付后关闭模型连接。

无行动回复直接归档关闭。被拒绝、取消、异常中断也有明确终态，不能永久占用 Agent 的推理锁。执行结果不明时先向执行器按 action_id 核实，不把网络超时当作“行动失败，可以再来一次”。

Loop 记录包含 `loop_id`、`trigger_ids`、`request_id`、`agent_id`、`timeline_id`、`state`、`started_at`、`goal_refs`、`event_watermark`、`resource_revision`、读取/压缩/费用计数、`decision_id`、`action_ids` 和结束原因。原有 request_id 继续标识模型决策传输，loop_id 关联跨越网络与游戏执行的全过程。

## 13. 定时驱动与事件驱动

### 13.1 触发规则

| 触发来源 | 处理方式 |
|---|---|
| 定时器 | 按职业/个体配置产生检查机会；活跃执行器正在正常推进时不重复规划同一工作 |
| 玩家对话 | 高优先级启动对话 Loop，检索相关记忆，允许形成短期目标 |
| 工作邀请、交易报价、委托变化 | 对相关参与者产生事件触发，带实体 ID、版本和事实摘要 |
| 重要环境或社会变化 | 只对有权限感知且与其目标/活动有关的 NPC 唤醒，其余只记事件 |
| 行动批次完成、失败或受阻 | 聚合实际结果，存在后续目标、待处理问题或值得重新选择的状态时唤醒 |
| 短期目标到期或约定检查时间 | 产生一次目标检查事件，核实完成条件、继续、推迟或放弃 |

**事件持久化和事件唤醒是两个独立决定。** 所有有意义的行动、回复和结果都进入历史，但 `DecisionRecorded`、读取回执、普通 `speak`、记忆提取完成、上下文压缩完成等不会因为被记录就唤醒自己。

`wait` 安排有界的下一次检查或等待条件；不会在记录 wait 完成后立即再次唤醒。项目或批次内部步骤成功只记录状态，默认由执行器续行；整个批次/项目完成或真正受阻才交回模型判断。

### 13.2 调度与并发

每个 NPC 同时最多一个正在构建上下文/推理/提交的 Loop。多个事件合并为一次唤醒，保留全部 trigger/event 引用；不能像覆盖单个 pending 槽位那样遗失低优先级事件。

配置优先级、合并窗口、连续反馈冷却和每时间段 Loop 上限。建议后台事件默认合并 1 个游戏分钟，玩家对话不等合并窗口；连续由自己行动反馈驱动的链默认最多 3 个 Loop，之后推迟到冷却后的计时事件，不删除事件或目标。新外部重要事件可按优先级提前调度，但仍受总预算控制。

定时周期从最近一次有效后台检查/执行批次结束后计算；异步执行期间重复的定时到期合并为一个待检查标记，结束后不补发几十次过期定时调用。纯对话不重置自主经营的检查周期。

游戏执行器与推理锁分开管理。旧 Loop 正在异步执行时，允许新的对话 Loop 读取其状态和与玩家交流，但动作调度器限制同一 NPC 同时只能有一个占用移动/劳动的执行链。新行动只能排队、明确替换尚未提交部分，或通过既有取消工具请求在安全点停止；不能凭一次新模型回复覆盖已扣款订单。

对话抢占只取消尚未提交的后台推理，实际已提交动作继续由执行器负责。旧 Loop 的迟到模型响应因失效 lease/epoch 被拒绝；旧动作真实回执仍正常写入历史。对话期间到来的执行结果先入库并标记上下文待刷新，避免又并发打开一个反馈推理 Loop。

## 14. 从对话和事件形成短期目标

### 14.1 目标的含义

人格和职业目标是稳定动机；短期目标是针对当前信息产生的具体意图，例如“了解面包需求，判断今天是否值得加工一批出售”。短期目标可以跨多个 Loop 持续存在，并在查询和执行后修订。

玩家说“市场最近可能缺面包”只形成信息来源，不直接形成已接受订单。NPC 可以依照人格和资源主动采纳调查/经营目标，也可以不采纳。涉及双方交易或任务承诺时，仍通过已有提议/接受工具形成真实协议。

### 14.2 目标数据与工具

新增 `ShortTermGoalStore`，由 Godot 管理结构化目标和版本并随游戏存档保存；服务端只保留事件/记忆投影。字段建议：

```text
goal_id, actor_id, version
description, motivation
source_event_ids, related_entity_ids
priority, status
created_at, review_at, expires_at
success_condition, progress_refs
last_reviewed_at, resolution_event_ids
```

状态：`active / blocked / completed / abandoned / expired`。同时活跃目标默认最多 3 个；优先级和有效期必须有界。到期自动转 expired 并产生一次记录/检查机会，避免永久挂起。

拟定行动工具：`adopt_short_term_goal`、`revise_short_term_goal`、`abandon_short_term_goal`。它们计入本轮行动上限，记录目标状态变化事件。纯文本说“我准备做”不会暗中落成目标；目标工具执行成功后才算已采纳。

客观完成条件使用白名单谓词，例如持有物品数量、获得指定报告、真实交付完成、指定项目完成；由实际状态/回执判定。开放式目标允许模型通过修订工具提交“已达成”的建议及来源引用，由系统校验；无法客观验证的主观决定记录为“结束追求/放弃”，不虚构完成证据。

新增目标不必再制造一个立即唤醒自身的事件。如果本轮还可提交行动，可在同一批中继续执行已充分确定的动作；否则按 `review_at`、对话结束/恢复游戏事件或相关外部事件唤醒。目标工具默认不预留资金，涉及花费仍由实际行动/项目工具核验和托管。

初始头部继续保持四块。最近目标变化出现在 15 条事件中；本轮被唤醒的目标在 `turn.goal_refs` 中只提供 ID、简短目标和最后已知状态，作为触发依据，不加载全量目标列表。普通定时检查按优先级选择少量到期活跃目标引用，任务/目标详情按需读取。

### 14.3 示例

1. 玩家：“今天也许有人收面包，你可以去看看。”
2. 对话 Loop 根据人格、金币和面粉库存，决定调用 `adopt_short_term_goal`，记录“核实需求并考虑加工面包”。回复“我会先去核实需求”，不能说已经赚到钱。
3. 对话结束且游戏恢复后，目标的检查事件开启新 Loop；NPC 查询市场/委托，需要加工时才查询配方和建筑。
4. 模型确认条件后调用 `rent_production` 或提交生产项目，游戏执行走路、排队和结算。Loop 进入等待执行。
5. 成品交付事件更新资源和历史；若仍需销售，反馈触发新 Loop，重新查询最新需求并选择出售、交付或继续持有。
6. 完成条件满足后记录目标完成；没有其他待处理目标就等待下一次事件/定时器。

## 15. 行动就是可执行工具

### 15.1 工具执行契约

模型调用 `move`、`plant`、`build`、`rent_production`、交易/目标等类型化行动工具，Agent 运行时自动路由到 Godot 执行器。无需开发者手动应用模型生成的计划。

行动工具声明：参数 schema、权限、执行资源类别（移动/劳动/非占用）、即时或异步、前置条件、费用/数量上限、完成标准、取消规则和可能产生的事件。

- `move`：路径可达性校验 → 开始移动 → 到达才 completed。
- `plant`：校验真实地块/种子 → 走到作业位置 → 执行种植并按领域规则消耗种子 → 地块状态提交后 completed。
- `build`：校验地点/类型/材料 → 按真实规则预留和施工 → 建筑完成后 completed；不是出现模型文本或创建施工任务就完成。
- `rent_production`：按现有定义经过接单、排队、加工到成品交付，工具说明明确 completed 的具体边界。
- 仅负责创建长期项目/订单的工具，其 completed 只表示项目/订单成功建立；项目另有生命周期和结果事件，不能冒充生产/建设最终完成。

执行状态统一为 `proposed / accepted / queued / in_progress / completed / failed / rejected / cancelled`。这是目标协议的扩展状态集；需更新 TS/Godot 校验器，不能仅增加 prompt 文案。

### 15.2 有上限的有序批次

默认自主 Loop 最多 3 个行动，对话最多 1 个；读取不占行动名额，目标管理动作占用名额。普通文字回复不额外算一个行动；同时有 `speech` 和 `speak` 时以明确输出规则去重，避免记录/展示两次同一句回复。

整批先验证工具名称、权限、参数形状和最大数量；非法批次不执行任何部分。合法批次依次运行，每一步执行前检查当前资源、目标状态和实体版本。

遇到异步行动，后续行动持久排队，等待它真正完成后再核验执行，不要求“异步动作必须放最后”。因此需同步移除当前 Provider 中要求 travel/build 放最后的提示，改为与执行器实际续行契约一致。失败/拒绝/取消时默认停止并将剩余动作标为 skipped，已完成步骤的真实效果保留。skipped 是批次步骤结果，不冒充工具被执行后的失败。批次不是跨多个真实行动的原子事务。

模型不能在一批中猜测尚未生成的建筑或订单 ID。步骤需要动态产物、复杂依赖或资源托管时使用现有项目工具，或等待结果开启下一 Loop；不在本次重构中另造一套通用项目语言。

执行中不反复询问模型“下一帧往哪走”；导航、动画、劳动、排队和已有项目图由确定性游戏逻辑推进。对话中可用行动继续受模式权限限制；允许排队的动作在暂停期间只返回 queued，恢复游戏后重新核验执行，不能因通用 Loop 支持行动而自动扩大对话权限。

## 16. 行动历史、结果反馈和下一轮上下文

每批及每个行动持久记录：`loop_id`、`decision_id`、`action_id`、幂等键、相关 goal_id、工具名、参数、事件类型、当前状态、发生时间、实际资源变化、受影响实体、失败原因、结果引用。重要阶段写事件，不记录逐帧运动数据。

至少覆盖 `DecisionCommitted`、`ActionAccepted`、`ActionStarted`、`ActionCompleted/Failed/Rejected/Cancelled` 和 `BatchFinished`。整批结构被拒绝也记录 `DecisionRejected`；原始模型输出保留在 trace，拒绝记录不是已完成行动。

资源结算和成功事件的产生由领域实际提交路径保证。需要动作实际扣费的时刻即更新资源投影，并可靠写入 outbox；不能先写完成事件后发现资源提交失败。多个系统对同一次事实的通知按来源/阶段去重，同时保留必要的因果关联。

行动完成后的顺序：

1. 提交真实资源/世界状态，并记录行动结果与批次状态。
2. 刷新 NPC 资源镜像、最近 15 条事件、历史摘要待更新区间、相关目标状态；队列化重要记忆提取。
3. 重建可供下次使用的上下文材料，并标记材料对应的事件/资源版本。此步骤不调用决策模型，也不重新加载其他领域。
4. 根据触发策略产生/合并反馈事件，结束原 Loop；已有批次后续步骤仍在运行时不触发重复规划。
5. 下一 Loop 真正派发前再次核对资源和事件水位，并基于新的输入检索记忆，生成新上下文。不能直接复用步骤 3 的旧缓存。

新 Loop 通过 `turn.trigger_event_refs` 带上促成本轮的最新结果引用/简述，事实正文优先在最近事件或按需详情中读取。触发事件因高流量已退出 15 条窗口时，仍能按引用查询，不为保留触发而把窗口扩成 16 条。

`BatchFinished` 可以包含各行动的简短结果与引用；与 ActionCompleted 同时存在时，两者保留各自事件身份，叙述内容避免复制大 payload。决策摘要、行动意图、实际执行回执和长期记忆不得互相替代。

## 17. Loop 内上下文自动压缩

### 17.1 三种压缩分别管理

| 机制 | 何时运行 | 产物 |
|---|---|---|
| 事件历史摘要 | 最近事件超过 15 条 | 持久历史摘要，覆盖更早经历 |
| 长期记忆提取 | 重要事实被可靠接入后 | 可相关检索的持久事实记忆 |
| Loop 工作上下文压缩 | 本轮输入大小超过阈值 | 本轮 continuation_summary，不自动成为长期记忆 |

Loop 压缩的目标是让模型保留当前任务进展和已获事实继续推理；不是让模型每次忘记工具结果重查，也不把它的推测写入长期记忆。

### 17.2 配置和触发

建议在 Agent Service 非敏感运行配置中加入以下起点，具体值按实际模型窗口调整：

```json
{
  "loop": {
    "max_read_rounds": 6,
    "max_read_calls": 12,
    "max_actions": 3,
    "max_dialogue_actions": 1,
    "max_feedback_chain": 3,
    "context": {
      "compact_at_tokens": 12000,
      "compact_target_tokens": 8000,
      "max_input_tokens": 16000,
      "max_compactions": 2,
      "recent_events_limit": 15
    }
  }
}
```

这些是配置示例，不表示当前 Provider 已支持或设置了对应窗口。启动时验证 `target < compact_at < max_input`，并用实际模型窗口减去最大输出和安全余量约束有效上限；配置超限时明确报错，不盲目发送。

每次模型调用前、工具结果批次加入后检查总输入，包括 system/user、工具 schema、完整 assistant/tool 历史和已有摘要。使用与模型匹配的 tokenizer；没有匹配计数器时使用保守估算并在 trace 标记估算，不把字符数当精确 token。

达到阈值即自动压缩，无需 NPC 调用压缩工具或玩家确认。在完整工具批次结果收齐后进行，不保留半个 tool_call。若单条结果会直接超硬上限，查询端先分页/缩小返回体，不能先生成一个超大 prompt 再尝试压缩。

### 17.3 保留与压缩规则

始终保留 GameEnv、身份/人格/目标、完整最新资源、当前玩家输入/触发依据、最近 15 条事件的既定表示，以及有效工具权限与剩余预算。身份、金币、背包数值不能由摘要重写。

工作压缩摘要包含：本轮要解决的问题、已查到的有来源事实、对象 ID/版本/观察时间、仍未知的关键问题、已排除选项的简短原因、待核实条件、下一步信息需要。只保留可解释的结论和事实，不要求保存内部逐步推理。

旧的重复列表、已被更新替代的观察、无关领域详情可压缩成摘要与 observation_id。当前准备行动所依赖的准确条款、金额上限、实体 ID、截止时间和版本保留结构化原值；确需逐出时标记必须重查，不把约数当精确值。

压缩后重新生成合法 messages：固定内容 + 相关记忆 + 有来源的 continuation_summary + 最近必要的完整工具轮次。被移除的 assistant/tool 调用成对移除；已有完整记录留在审计存储。不能同时保留被压缩的大块原文，从而只增加一段摘要而不减少体积。

摘要中的观察仍保留原时间，不因为压缩而刷新有效期。多个版本冲突时最新授权观察为当前依据，旧记录作为历史；无法确定时保留冲突并要求核实。

### 17.4 失败与循环边界

先做确定性去重/失效淘汰，再做有界模型摘要。摘要失败使用结构化事实摘录降级，保留原始存储，不无限重试。每次压缩后重新计量，低于 target 再继续；max_compactions 到达后停止新增大批读取并收束决策。

固定必带数据本身超过硬上限时，不能通过压缩丢掉真实资源或玩家问题。若配置模型无法容纳，返回明确的 `context_capacity_exceeded` 并保留输入/事件，不执行未经完整上下文支持的动作；这是容量配置异常，不声称模型已正常完成决策。

压缩仍在原 loop_id 内，读取数、已耗 token、超时、格式纠错、工具权限和行动上限不重置。`ContextCompacted` 仅进调试追踪，不作为游戏事实触发下一 Loop，也不占最近 15 条生活经历。

## 18. 本次补充的实施影响与验收

在第 9 节模块基础上增加：

| 模块 | 职责 |
|---|---|
| `AgentLoopCoordinator` | loop_id、状态转换、推理 lease、执行等待与终态归档 |
| `AgentTriggerQueue` | 定时/事件合并、优先级、目标检查、反馈链防自激 |
| `ShortTermGoalStore`（Godot） | 短期目标的采纳/修订/放弃、版本、完成判定与存档 |
| `ContextCompactor`（TS） | 输入计量、阈值检查、合法消息重建与压缩预算 |

`AgentLoopCoordinator` 协调现有 scheduler/gateway/executor，不复制导航、种植、建造或项目引擎。Godot 保存异步批次、幂等回执、目标和触发队列；服务端保存事件/记忆及 Loop 元数据。重启后未提交的推理可标记中断并重新排队，已提交动作必须恢复/核实原执行，不能再次提交同一动作。读档隔离规则沿用第 8 节。

实施顺序补充为：先完成事件/资源/记忆基础；再实现触发队列、短期目标、按需工具和执行反馈；随后切换统一 Loop 与自动压缩；最后集成验证。上下文重建与后台摘要失败不能阻止已经接受的合法游戏动作继续执行。

新增验收场景：

- 定时和多个事件同时到来，只派发一个推理 Loop，全部触发引用可追踪；纯读取、日志和压缩不会自激发下一轮。
- 对话消息促成一个有来源的短期目标，存档/重启后仍在；闲聊或假设不自动变成交易承诺；目标上限、到期和版本冲突生效。
- 模型可通过多轮读取后提交种植/建造等动作，游戏执行可见移动和真实状态更新；模型文字不冒充执行结果。
- 批次最多 3 个动作，异步第一步完成后再执行第二步；失败停止剩余步骤，已完成效果保留；无重复扣费。
- 资源和 event history 在每次结果提交后刷新；下一 Loop 包含最新结果且按新情境检索记忆，不带整轮旧工具垃圾。
- 旧执行 Loop 等待期间可对话；对话抢占不取消已提交世界动作，迟到模型输出不再次执行，实际迟到回执仍被记录。
- 多次动作反馈可以推进同一目标，同时反馈链上限/冷却避免无进展循环；到限后目标与事件仍可在下次检查继续。
- 输入超过压缩阈值时在同 loop_id 自动压缩；资源、15 条事件、目标来源和精确行动条件保留，消息 tool_call 配对合法，预算没有重置。
- 摘要服务失败、超大单条读取结果、必带头部超容量和连续两次压缩都有确定结果，不发生无限重试或无依据行动。
