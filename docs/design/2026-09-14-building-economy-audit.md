# 建筑与经济系统第一轮摸排

日期：2026-09-14。范围：正式 3D 入口、共用建筑/生产规则、NPC Agent 工具、当前存档。只读检查业务代码及存档，执行已有隔离测试；本轮不调整玩法或资产。

## 主要判断

现有建筑经济底座比 3D 操作入口和 NPC 能力覆盖得更广。17 类建筑都进入玩家建造目录，但只有 5 类使用正式 3D 专用模型，只有 4 类接入当前建筑点击面板。不能把“目录存在”“生产规则存在”“玩家能够操作”“NPC 能够经营”视为同一件事。

近期最有价值的接入是现有食品链的收货和流通，然后扩展建材与资源链。通用资产、订单、市场和维护系统可以复用，不需要为每座建筑重新实现一套金币系统。

此外，旅店、合作社等组织已经参与工资、食品采购、培训等经济行为，但不在上述 17 类可建造实体目录中。培训目前是 `ingredient_selection`，收费 30 金币、占用 120 分钟；不能据此视作已有完整旅店/学校建筑经营玩法。

## 当前真实流通断点

读取时的正式存档有 5 座建筑，均为玩家所有：风车 1、食品工坊 1、蜂箱 2、鸡舍 1。

| 位置 | 读取时的库存 |
|---|---|
| 食品工坊待收产物 | 面包 26、果酱 9 |
| 鸡舍待收产物 | 鸡蛋 6 |
| 一座蜂箱待收产物 | 蜂蜜 2 |
| 市场 | 面包 0、鸡蛋 0、面粉 42、谷物 77、蜂蜜 22 |

这是建筑库存与市场库存之间的流通断点，不能仅凭这份快照认定生产不足。鸡舍的蛋篮已达到容量上限。玩家的成品不属于其他 NPC，不能通过让 NPC 自动取走来解决短缺。

可补充的合法路径是：所有者自行收货出售；所有者发布采购/收货/配送/代售条款；NPC 查询报价后提出购买，由所有者授权成交。现有工作合同支持配送、供货和加工，但还不能把任意建筑输出容器作为通用货源，也没有鸡舍投料合同。

## 可以复用的底座

- `BuildingInstance` 保存 owner_id、稳定 instance_id、经营政策、生产状态及订单记录。
- `BuildingServiceSystem` 已有报价、原料与费用预检、排队托管、开工付给业主、完成交付、未开工取消退款、所有者维护和政策版本检查。自产不向自己收加工费。
- `ProductionSystem` 统一配方、队列、周期、输出上限、维护、部分升级；有事件通知。租用并不自动出售成品，原料成本也不包含在加工费里。
- NPC 市场交易修改真实余额和市场库存；项目可托管预算/材料，雇佣合同可托管工资并按真实履约结算。
- NPC 可用 `query_world(buildings/list|detail|sites)` 逐步发现建筑，使用 `rent_production`、`manage_building` 和项目工具行动。3D 实体建设走项目系统，只开放 windmill / food_workshop；旧抽象 build 已从 v3 菜单移除。

## 接口与规则缺口

1. **发现不够完整。** buildings/list 只列已有实例，没有完整可建类型/能力目录。detail 主要返回 ProducerState、费表、政策；没有按类型接入蜂箱花田分配、鸡舍缺料、资源周期、温室种植位、水车覆盖、仓库容量等专用快照。无 producer_state 的功能建筑会返回空生产对象。
2. **关键操作缺少 Actor 接口。** NPC 没有投料、收取自产、仓库出入库、资源深度调整等动作；维护/定价能做，不等于完整经营。现有通用投料入口以 InventorySystem 为参数，收货入口多处按 player/customer_outputs 处理，扩展前需统一操作者与货权核验。
3. **3D 界面落后于共用系统。** 当前点击只接受风车、食品工坊、蜂箱、鸡舍。其他建筑即便建出来，也不能因此认为玩家已经有操作入口。
4. **物权与收益边界不统一。** 蜂箱按花田分配，鸡舍/资源建筑产物留在 building.outputs，加工订单按客户交付。谷仓附近收集的旧实现按范围枚举 state.outputs，未在枚举处过滤所有者；在 NPC 资产推广前需要审计，不能直接开放为跨所有者自动收货。
5. **缺少统一建筑经营账。** 已有订单、付款与项目回执，但查询接口没有提供建筑维度的期间收入、耗料成本、维护费用、库存占款、产能利用率、停产原因。NPC 很难比较“自产、外包、投资新建”的实际收益。
6. **被动资源生产还不等于产业经营。** 当前产量由时钟、储存空间和维护控制，没有劳动力工资/工具损耗投入。若加入雇佣，应明确工时如何影响产量，避免新旧两套机制同时产货。
7. **需求端不宜只靠市场兜底。** 食物已有居民消费、旅店采购和活动采购；建材有建设与维护消耗。后续纺织/精制品应对应明确的居民或组织需求，再评估产能和价格，不应只按目录参考价计算利润。

## 建议接入顺序（待后续设计）

1. 先贯通现有食品链：鸡舍/蜂箱专用查询、授权投料与收货、建筑库存采购/配送、产物进入市场。用“市场缺蛋但鸡舍满仓”作为第一条验收场景。
2. 补工作台、石窑、熔炉：优先补 3D 可操作性与 NPC 实体建设，复用收费加工，打通建材供应和设备维修需求。
3. 接伐木场、采石场、矿场与谷仓：先明确货权、仓储和运输，再决定劳动力/工具成本；已有被动周期与新经营规则只能结算一次。
4. 接温室、水车、水井：把真实生产效果、覆盖范围、受益者、维护付款方做清楚，再设计租赁/服务收费。
5. 纺织与精制品随实际需求扩展；路灯、围栏作为建设订单和公共设施处理。

每类接入沿同一链路验收：按需查询 → 核实报价/库存/权限 → 实际到场执行 → 原子资产结算 → 完成事件 → 下一轮 Agent 决策。初始 context 不再塞入所有建筑细节。

## 本轮验证与限制

- 3D 鸡舍：50 项通过；3D 蜂箱：61 项通过。
- 共用生产：407 项中 405 项通过、2 项失败。失败来自同一存档用例把 gx=-1 视为非法；当前扩展地图与 BuildingInstance 允许负坐标，需更新旧用例并另行验证占地一致性，不能把这次测试报告为全通过。日志中的另外三条事务错误来自故障注入用例。
- 未重跑所有旧建筑的 3D 操作、跨业主收货或真实 LLM 经营；表中这些缺口主要由调用路径检查确认。
- 本轮没有修改业务代码、玩家存档、市场库存和 NPC 资产。
