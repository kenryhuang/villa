# Agent 容量与实体建造修复

## 容量根因

检查 `tmp/farm3d-65b8e5d8cc470-106f000f19c-1789516873-3303606.ndjson` 时，已有记录中出现 8 次 `context_capacity_exceeded`。并非没有压缩：部分请求已执行两次，但固定头部加工具定义约占 18–26 KB，超过旧的 16,000 压缩目标。后续查询继续累积，常规压缩两次的限制阻止了再次恢复，最终超过 32,000 硬上限。

当前配置如下，示例配置和本机配置同步更新：

| 配置 | 旧值 | 新值 |
| --- | ---: | ---: |
| compact_at_tokens | 24,000 | 48,000 |
| compact_target_tokens | 16,000 | 32,000 |
| max_input_tokens | 32,000 | 64,000 |
| max_compactions | 2 | 6 |

这些值实际按 UTF-8 字节保守估算，包含消息与工具定义，并非模型的精确 token 数。每轮调用前计算容量；有效压缩目标参考固定头部及工具定义的大小，为观察结果留出空间，但保持在硬上限以下。超过硬上限时，即使常规压缩次数耗尽，也再次尝试压缩；读取次数、行动次数和 Loop 时间预算不重置。

保留已有结构化压缩方式：完整保留或丢弃单条观察，保留报价、ID、前提、时间与版本；缺失内容要求重新查询。固定头部自身过大仍会失败，不能通过删除人格、资源或伪造截断数据来绕过限制。

`context.compacted` 新增配置目标、实际目标、保护内容大小和触发原因；失败前的 `context.capacity_exceeded` 区分固定内容超限与工作上下文超限。

## 实体 build

旧的 3D Loop 主动移除了 `build`，旧执行入口只支持抽象建筑。现在使用现有持久化项目、材料托管和实体施工系统：

1. `discover_tools` 打开 `buildings`，`query_world` 查询 `sites`。
2. 场地返回实际成本、接近位置和精确的 `build_action`。支持 `windmill`、`food_workshop`，参数为 `building_type`、`gx`、`gz`。
3. `build` 检查角色日程、场地与材料，托管自己的材料，创建幂等项目。
4. 项目依次预留土地、步行到现场、开始施工、等待实体完工。
5. 启动返回 `in_progress`；实体完工后才记录完成，并继续同批后续行动。阻塞返回项目 ID 与重试/取消入口。

项目 ID 根据行动幂等键生成，保存加载后继续关联；调度仅豁免该建造项目自身等待中的批次续行，防止二者互相等待，其他角色工作冲突仍正常阻止。新建筑属于建造 NPC，默认不对外开放，可通过现有服务策略接口开放经营。旧 2D 建造契约保持兼容。
